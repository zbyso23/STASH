## Milestone 3 — blob I/O, buffer pool, crash simulation (done)

| Package | Content | SPEC |
|---|---|---|
| `internal/vfs` | `FS`/`File` interface with positional I/O (pread/pwrite); `OS` implementation (POSIX directory fsync); `ReplaceFile` (tmp → fsync → rename → fsync dir); bounded `ReadFile` | §2.1.1, §18 |
| | `CrashFS`: in-memory FS with an explicit durability model (data durable on `Sync`, names on `SyncDir`) and three crash models: drop unsynced, tear unsynced pages at 512-byte sectors in any order, and tear with garbage sectors (storage without atomic writes) | §3.1.1, §17 |
| `internal/bufpool` | power-of-two size classes 4 KiB–16 MiB, bounded free lists, total retained-bytes cap (default 256 MiB); sizes only from validated values | §16.1 |
| `internal/frame` | `AppendFrame(dst, …)`: encodes into a caller buffer with no heap allocation; padding zeroed explicitly so a reused buffer never leaks | §6 |
| `internal/blob` | `Create` (durable header), `Open`/`Reader.ReadFrame`, `Scan` through a pooled 1 MiB read-ahead window (VARIABLE and FIXED), `ProbeTail` (every grid offset, also inside found frames), `OpenWriter` with the torn-tail rules (truncate, or SEALED when a `loc` offset ≥ E or a referenced `group_id` lies beyond E), `Writer.Append` with serialized allocation and parallel build/write, `Sync` that waits for in-flight writes below it (no holes before durable frames), poisoning after a write or fsync failure | §2.4, §3, §10.4, §10.4.2, §11.1–§11.3, §12.2 |

The torn-tail decision takes `blob.Committed` (highest referenced offset in the blob, and a group predicate); the manifest milestone will supply it.

Tests: synced frames survive 300 seeds of torn crashes and the tail is truncated; pages persisted out of order; an embedded archive frame in a payload; a referenced group beyond E; a damaged committed frame seals the blob; on garbage-writing storage no committed frame is ever silently truncated (some seeds seal, as §3.1.1 predicts); shared page with the previous frame stays unchanged; crash at every step of `ReplaceFile` yields old or new content; 8 concurrent appenders under `-race`; injected I/O error poisons the writer.

Benchmarks (`go test ./internal/blob ./internal/frame -bench . -benchmem`): `AppendFrame` 0 allocations per frame (`Build` 4), append and scan with and without the pool. Throughput is bound by SHA-256 (about 1 GB/s per core here) and by the filesystem, so the pool mainly removes per-frame garbage (64 KiB to 16 MiB per frame) and GC pauses under load rather than raising single-thread throughput.

The crash tests found a gap in §10.4.2: a committed frame damaged by a non-atomic shared-page write did not validate and would have been truncated as a torn tail. SPEC now says a `loc` at or beyond E seals the blob (Erratum row E1-18).

`blob.Committed` now holds the referenced frames by identity (`frame_hash` + path + file_ver + logical offset), because `loc` carries no physical offsets: a blob is SEALED when a referenced frame is missing from the valid run before E.

Tests: canonical lines equal byte for byte an independent Python encoder (`testdata/gen/gen_golden_m5.py`), 4 non-canonical valid lines accepted, 46 invalid lines rejected (including invalid, overlong and surrogate UTF-8); fold rules; the E1-4 case `ADD_BEGIN(v8), ADD(v9), ADD_COMMIT(v8)`; 1,100 crashes inside transactions leave the manifest readable (E1-1); 300 torn crash seeds (both torn forms) keep every synced record and only an in-order prefix of the rest; linked manifests merge by seq, 8 kinds of link corruption fail closed; end to end, the manifest decides the blob torn tail and a damaged committed frame seals the blob; fuzz `FuzzDecodeLine` (accepted lines must round-trip canonically).

Performance: appending an ADD with 17 extents about 45 µs (in-memory FS), loading about 65 MB/s of manifest per core. A faster decoder that skips the generic JSON tree is a later optimization.

SPEC changes: E1-18 restated by frame identity; E1-20 a manifest line containing NUL starts the torn tail (found by the crash tests: out-of-order page persistence otherwise bricked the archive after an ordinary crash).

Not yet: encrypted envelopes (`*_ENC`, crypto milestone), HARDENED anchored length on the writer side, spilling staged extents to disk.

Tests: allocator values are always below a durable `reserved_through`, never reused across 200 torn-crash seeds, identity mismatches and a missing file fail closed, rollback detected, re-initialization saturates; a crash at each of 60 steps of `Create` leaves a complete archive or `ErrIncomplete`, never a half-valid one; crashes at hundreds of points of a Put/Delete workload: every returned operation is durable, an in-flight one is all or nothing, the writer reopens without sealing and continues; a rolled-back `filever.alloc` is refused; a damaged committed frame seals its blob, the object reports `ErrMissingData`, writes continue on other blobs; 8 concurrent writers under `-race`; the same suite on the real filesystem with `flock`.

Performance note: `Put` of 64 KiB on the real filesystem is about 1.5 ms, dominated by two fsyncs per commit (blob, then manifest). Group commit (several Puts per fsync pair, §10.4) is the planned fix.

SPEC change E1-21: creation order and the incomplete STANDARD creation; the `file_ver` cold-start check covers every record, not only live versions.

## Milestone 7 — group commit and the public API (done)

Public package `stash` (module root):

```go
err := stash.Create(dir, stash.CreateOptions{})        // Variable/Fixed, SHA256/BLAKE3, Blobs, MaxFrameSize
a, err := stash.Open(dir, stash.Options{})             // writer lock + crash recovery
defer a.Close()
ver, err := a.Put("photos/a.jpg", data)                // durable when it returns
ver, err  = a.PutReader(ctx, "big.iso", file)          // streaming, bounded memory, cancellable
data, err := a.Get("photos/a.jpg")
obj, err  := a.OpenObject("big.iso")                   // io.ReaderAt + io.Reader + io.Seeker, lazy
err = a.Delete("photos/a.jpg")
info, err := a.Stat(p); paths := a.List(); h := a.Health()
r, err := stash.OpenReadOnly(dir)                      // lock-free snapshot
```

Paths are normalized to NFC; anything that is not a clean relative path is rejected with `ErrInvalid`. Errors: `ErrNotFound`, `ErrMissingData`, `ErrLocked`, `ErrPathBusy`, `ErrNoWritableBlob`, `ErrIncomplete`, `ErrCorrupt`, `ErrUnsupported`, `ErrInvalid`, `ErrResource` (use `errors.Is`).

Internals (`internal/archive`):

- **group commit** (§10.4): leader/follower without timers; the leader syncs the union of touched blobs in parallel, appends every queued record, and syncs the manifest once. A request whose blob sync failed is never referenced. Batches form exactly while a sync runs, so a lone writer pays no extra latency.
- **parallel extents**: the frames of one object are built, hashed and written by up to `min(GOMAXPROCS, 2 x blobs)` workers across blobs; `PutReader` reads into pooled buffers.
- **lazy object reader**: binary search over extents, one cached frame per object, frames validated on every fetch.

Tests: public round trip in VARIABLE/FIXED/BLAKE3, NFC equivalence and path rejection, streaming with short reads, random `ReadAt`/`Seek`, failing source and cancelled context leave the object unchanged and the path free, 16 concurrent writers, the single-writer lock; crash test of group commit (6 concurrent writers, batches of up to 3, every returned Put durable at every crash point).

Benchmarks on this container's disk (`go test . -bench .`): 64 KiB Put sequential about 56 MB/s (1.2 ms, two fsyncs), with 64 concurrent writers about 215 MB/s (group commit, about 4x); 64 MiB Put about 400 MB/s; 64 MiB Get about 800 MB/s. Numbers depend heavily on the disk's fsync latency.
